1. What it is

pystepflow runs a Python program under a tracer and records a complete snapshot of the program state at every step. The browser then lets you move through those snapshots: forwards, backwards, or jumping straight to a moment of interest.

At any step you can see the line about to execute, the full call stack with every local variable, the objects living on the heap with arrows showing which name points at which object, the output produced so far, and a flowchart of the code with the executed path lit up.

It is built for the moment when you know what a program does but not how it got there — recursion, nested loops, aliasing bugs, an agent loop that took an unexpected branch.

Design constraints

  • Standard library only. No pip dependencies at runtime. No CDN, no build step, no framework in the frontend.
  • Entirely local. The server binds to 127.0.0.1 and nothing is sent anywhere.
  • Crash-isolated. Traced code runs in a subprocess with a timeout, so an infinite loop cannot take the server down.

2. Installation

Requires Python 3.9 or newer. Verified on 3.14; the source is checked against the 3.9 grammar.

From PyPI

pip install pystepflow

From a local checkout

git clone https://github.com/2001-Ankit/pystepflow
cd pystepflow
pip install -e .

Without installing anything

python -m pystepflow.server

If pystepflow is not found after installing: pip put the executable in a Scripts directory that is not on your PATH. It prints a warning when this happens. Either add that directory to PATH, or use the equivalent python -m pystepflow.server form, which always works.

3. Quick start

pystepflow my_script.py

Your browser opens at http://127.0.0.1:8000 with the script loaded. Press Visualize (or Ctrl+Enter), then → to step forward.

With no file argument you get an empty editor — paste code into it, or pick one of eight built-in examples from the Examples… menu. The examples were each chosen to demonstrate a different part of the tool: recursion and the growing call stack, aliasing and shared references, a linked list of objects pointing at objects, closures capturing state, and an exception propagating up the stack.

Deep links

Adding #run to the URL traces immediately on load; #run@47 also jumps to step 47. Useful for bookmarking a preloaded file, or pointing a student at one exact moment.

http://127.0.0.1:8000/#run@47

5. Tracing a whole project

By default the tracer's boundary is a single file: a call into another module of your own is executed but not stepped into, exactly like a call into json. On a real codebase that means most of the interesting flow escapes the visualization. --project moves the boundary from "this one file" to "this project".

pystepflow main.py --project

The entry script is run from disk exactly as python main.py would run it, and every .py file under the project root is traced. The code panel follows execution from file to file, each frame in the call stack is labelled with its module, and the flow graph resolves the correct function even when two modules define the same name.

What is excluded, and why it has to be

Dependencies are never traced, even when they live inside the project root — site-packages, dist-packages, .venv, venv, env, __pycache__, node_modules, .git, .tox, build, dist.

Module bodies are also skipped as they are imported. That is not a detail: importing eleven standard-library modules costs about 264,000 line events, some fifty times the entire step budget, before a single line of your own program runs. Import-time code is class and function definitions rather than the flow you asked to see. Pass --trace-imports if you genuinely want it.

Use --include on anything large. Tracing stops at MAX_STEPS (5000). A substantial program will hit that long before it reaches the part you care about, so narrow the trace to the subsystem you are studying.

pystepflow main.py --project --root .                 # explicit project root
pystepflow main.py --project --include "services/*"   # one subsystem only
pystepflow main.py --project --exclude "*/legacy/*"   # skip part of the tree
pystepflow main.py --project --trace-imports          # include import-time code

Two practical constraints

  • Edits in the browser are ignored. Project mode runs the files on disk. Edit in your own editor, then press Visualize again. The code panel becomes a viewer rather than an editor.
  • Dependencies must be importable by the interpreter running the server. If the project uses a virtualenv, start pystepflow from inside it, or the entry script will fail on its first import.

What a cross-module stack looks like

Each frame carries its own file, so a stack can span modules:

main.py              <module>      line 24
main.py              process       line 16
services/pricing.py  price_order   line 7
services/pricing.py  discount      line 11   <- executing

6. The interface, panel by panel

Code

While editing, this is a plain textarea with line numbers. Once traced it switches to a highlighted view where colour encodes what each line is doing at the current step:

ColourMeaning
BlueThe line about to execute
VioletA line in a calling frame further up the stack, waiting for its call to return
GreenA return is happening on this line
RedAn exception was raised here

Press Esc or the Edit button to go back to editing.

Program state — call stack

Every active frame, innermost on top, each showing its local variables in a useful order: arguments first in declaration order, then other names as they appear. Values that changed since the previous step are tinted amber, so a stepping loop shows you exactly what moved.

Program state — objects on the heap

Primitives (numbers, strings, booleans, None) are shown inline next to the variable name. Everything else — lists, dicts, sets, instances, functions — lives in the heap column and the variable shows a clickable chip with an arrow drawn to the real object.

This is the part that makes aliasing visible. If two names point at the same list, you see two arrows converging on one box; if one is a copy, you see two separate boxes. Hovering a chip lights up its target and thickens the arrow; clicking scrolls to it.

Flow graph

A flowchart built from your code's own structure, not from the trace: sequential statements stack vertically, an if fans into two columns that merge again, a loop places its body under the test with a dashed back-edge routed down its own lane so nested loops stay readable.

The execution is then painted on top of that fixed shape:

  • Boxes that have run are filled in; boxes never reached stay empty.
  • Arrows actually taken turn blue — so you can see which branch was chosen.
  • A ×N badge counts how many times each box ran.
  • The current box is outlined in blue.

The graph follows you into whichever function is executing. Untick follow to pin one function, or choose another from the dropdown. Clicking any box jumps to the moment that line ran — inside a loop, repeated clicks walk forward through the iterations. Zoom with − / fit / +.

Call tree

The second tab: every call made during the run, nested by depth, with arguments and return values. Clicking a call jumps to it. This is the complementary view to the flow graph — the graph shows the shape of one function, the tree shows the shape of the whole run.

Input and output

Whatever you type into the Input box is fed to input(), one line per call. Program output appears incrementally: at each step you see exactly how much had been printed by that point, not the final output. Errors appear in red at the end.

8. What it can and cannot trace

Verified working

Each of these was tested end to end:

FeatureFeature
Functions, recursion, nested callsClasses, inheritance, methods
Generators and yieldList / dict comprehensions
Decorators, *args / **kwargsClosures and nonlocal
try / except / finallywith statements
Standard-library importsLambdas, sorted(key=…)
Dataclasses, pydantic modelsf-strings, walrus operator
asynciothreading
match statementsUnicode and bytes

Deliberately not stepped into

  • Library internals. Tracing stops at your file's boundary. json.dumps(...) shows the call and its result, not a walk through the json module. This is what keeps traces readable.
  • C-level code. sorted(), len(), NumPy operations are a single step, because there are no Python lines inside to show.
  • Other threads. Threaded code runs correctly and produces correct output, but only the main thread's frames are recorded.
  • Async event-loop internals. Your coroutines are traced; the loop's own machinery is skipped.
  • Terminal and GUI programs. Use the Input box for input(); curses and tkinter will not render.

9. GenAI and LLM code

Agent loops are one of the best things to point this at, because the control flow is exactly what is hard to hold in your head. Verified against agent loops with tool dispatch, retries, streaming, and pydantic response objects.

What you see is your orchestration logic, one line at a time: the message list growing turn by turn, which tool was selected, the retry branch being taken, chunks accumulating in the streaming loop. The flow graph shows the agent loop as a loop, with ×N counting the turns.

What you do not see is the inside of the SDK. client.messages.create(...) is a single step showing the call and the response object; the HTTP machinery inside anthropic, openai or langchain is not stepped through, the same as any other library. Response objects render well, since they are ordinary instances with attributes.

Raise the timeout

pystepflow agent.py --timeout 120

The 15-second default will kill a real model call. Size the timeout for the whole run, not one call — an agent doing five turns needs five turns' worth.

The calls really happen. Stepping through an agent loop costs the same in tokens and money as running it normally. Scrubbing back and forth afterwards is free, because you are moving through a recording — but the initial trace is a real execution.

Trace size

Every step re-snapshots your data, so large objects are expensive: a 1536-float embedding produced a 427 KB trace for a three-line program. Containers are truncated to 200 elements for display, but the traced portion still accumulates. Prefer tracing loop logic with a stub client over a 50-message production context.

10. Security and privacy

This is a tracer, not a sandbox. Your code really executes — file writes, network calls, os.system and everything else do exactly what they normally do. Only visualize code you would be willing to run directly.

Keep it on localhost

The server defaults to 127.0.0.1. Do not bind it to a public interface: the /api/trace endpoint executes arbitrary Python by design, so exposing it to a network hands anyone who can reach it a remote code execution primitive.

Secret redaction

Every variable ends up in the browser, where it may be screenshotted or shared. Values that are credentials are therefore masked before the trace leaves the tracer process, in the variables panel, in object attributes, and inside dictionaries.

A value is masked when either its name or its shape says credential:

RuleExamples
Names that always mean a credentialapi_key, password, secret, access_token, private_key
Ambiguous names, masked only if the value also looks secrettoken, key, auth
Value shapes, masked whatever the namesk-…, ghp_…, AKIA…, xoxb-…, Bearer …

The ambiguous tier matters in this domain: tokens, token_count, max_tokens, key and keys are everyday vocabulary and are verified to pass through untouched. Only a genuinely secret-looking value under those names is masked.

A key read from the environment never reaches the browser at all:

api_key = os.environ["ANTHROPIC_API_KEY"]
headers = {"x-api-key": api_key, "content-type": "application/json"}

# In the UI:
#   api_key  <redacted>
#   headers  {'x-api-key': <redacted>, 'content-type': 'application/json'}

One limit worth knowing. A key written as a literal in your source is still visible in the code panel and in flow-graph labels — that is your own source being displayed, not a runtime value. Read secrets from the environment if this matters to you.

Pass --show-secrets when you genuinely need to inspect the real value.

11. Limits and tuning

These exist to keep the browser responsive. All are constants at the top of pystepflow/tracer.py except the timeout, which is a CLI flag.

LimitDefaultEffect when exceeded
MAX_STEPS5000Tracing stops and reports how far it got
MAX_ITEMS200Containers show the first 200 elements, marked truncated
MAX_STRING300Strings are elided with an ellipsis
MAX_DEPTH8Deeper nesting falls back to a plain repr
MAX_OUTPUT200000Output beyond this is dropped
MAX_STATEMENTS (cfg.py)400No flow graph is drawn for that function
--timeout15 sThe trace subprocess is killed

Raising them is safe; the cost is memory and a heavier page. An infinite loop hits MAX_STEPS first and returns a clean error rather than hanging.

12. Using it as a Python library

from pystepflow import trace_code

result = trace_code("""
a = [1, 2]
b = a
b.append(3)
""")

print(result["step_count"])          # 4
print(result["steps"][-1]["stack"])  # frames, variables, heap references
print(result["graphs"][0]["nodes"])  # flowchart of the module

trace_code(code, stdin="", max_steps=5000, redact=True)

Traces a source string and returns the result dictionary described in the next section. Set redact=False to keep real credential values.

trace_project(entry, project_root=None, stdin="", max_steps=5000, redact=True, include=None, exclude=None, trace_imports=False)

Runs entry as __main__ and traces every module under project_root, which defaults to the entry's directory. The result gains sources (one entry per file that ran), files, entry, and mode == "project"; every step and every frame gains a file.

from pystepflow import trace_project

result = trace_project("main.py", include=["services/*"])
print(result["files"])        # ['main.py', 'services/pricing.py', ...]
print(result["steps"][30]["file"])

serve(port=8000, host="127.0.0.1", file=None, workspace=None, open_browser=True, timeout=None, show_secrets=False)

Starts the web server. Blocks until interrupted.

from pystepflow import serve
serve(port=8000, file="my_script.py", timeout=120)

13. How it works internally

The tracer

tracer.py installs sys.settrace and records a snapshot on every line, call, return and exception event whose frame belongs to your file. Frames from anywhere else return None from the trace function, which is what stops execution descending into library code.

Each snapshot walks the frame chain from the module level down to the current frame and encodes every variable. Primitives are inlined; everything else is written into a per-step heap keyed by a stable id. Objects are kept alive for the duration so CPython cannot recycle an id and make two different objects appear to be the same one. That stability is what makes the reference arrows and the aliasing view correct.

Self-referential structures terminate because a placeholder is inserted into the heap before an object's contents are encoded.

Two details worth knowing: the module body is reported by CPython as a call event at line 0, which is an artefact of exec() rather than something you wrote, so it is skipped. And stdout is captured to a buffer, with each step recording the buffer length at that moment — which is how the output panel can show you exactly how much had been printed at any given step.

The flow graph

cfg.py parses the same source with ast and lays out one flowchart per function, recursively. Each fragment reports its width, height, and the x of the vertical spine that flow enters and leaves on:

  • A block of statements stacks its children vertically, aligning their spines.
  • An if places the test on top, the two branches side by side beneath it, and a merge point below both. If both branches end in return, the merge is dropped as unreachable.
  • A loop puts the body under the test and adds a back-edge from each body exit to the test, with margin reserved on the left so the edge has a lane to travel in.

The browser receives finished absolute coordinates and only has to draw them. Layout is done in Python because the recursion mirrors Python's own nesting.

Execution overlay

Given a step, the browser replays every earlier step belonging to the same frame invocation, maps each line to its node, and counts visits. Transitions between consecutive lines are resolved to a chain of edges by walking the graph through merge points, which have no source line of their own. That is how a branch arrow gets lit without lighting its sibling.

The server

server.py is a stdlib ThreadingHTTPServer. The only interesting decision is that /api/trace spawns a subprocess rather than tracing in-process. That buys crash isolation and a hard timeout: a runaway loop, a segfault, or a sys.exit() in your code affects only the child.

The child writes its JSON result after a marker string, so anything the traced program printed directly to the underlying file descriptor is discarded rather than corrupting the response.

EndpointPurpose
GET /The UI
GET /static/…Assets, with directory traversal refused
GET /api/preloadThe file given on the command line
GET /api/open?path=…A .py file inside the workspace
POST /api/traceTrace {code, stdin}, return the result

14. Data formats

Trace result

{
  "steps": [ … ],           # one snapshot per event
  "stdout": "…",            # complete output
  "stdout_truncated": false,
  "error": null,            # or {type, message, line, traceback}
  "code": "…",              # the source that was traced
  "step_count": 90,
  "graphs": [ … ]           # one flowchart per function
}

A step

{
  "i": 42, "event": "line",   # call | line | return | exception
  "line": 7, "func": "fib", "depth": 3,
  "stack": [ {fid, func, line, is_global, vars: [{name, value}]} , … ],
  "heap":  { "4": {id, kind, type, items, …} },
  "out": 128                  # chars of stdout printed by this point
}

A value

{"t": "prim", "v": 42, "d": "42"}   # inlined
{"t": "ref",  "id": 4}              # points into that step's heap

Heap object kind is one of list, tuple, set, dict, instance, function, class, module, or opaque.

A graph

{
  "name": "fib", "signature": "fib(n)",
  "first_line": 1, "last_line": 4,
  "width": 502, "height": 898,
  "nodes": [ {id, kind, label, line, x, y, w, h, calls} ],
  "edges": [ {from, to, kind, label} ]
}

Node kind: start, stmt, cond, loop, return, raise, break, continue, def, merge, end. Edge kind: seq, true, false, back.

15. Project layout

pystepflow/ ├── __init__.py public API: trace_code, serve, main ├── tracer.py sys.settrace snapshots → JSON, secret redaction ├── cfg.py ast → laid-out flowcharts ├── server.py http.server, /api/trace, subprocess isolation └── static/ ├── index.html layout and panels ├── style.css the whole visual design ├── app.js stepping, stack/heap rendering, reference arrows ├── graph.js flow-graph SVG and execution overlay └── examples.js the eight built-in programs

No build step. The frontend is three plain files loaded directly by the browser; editing them and reloading is the entire development loop.

16. Publishing a release

Prerequisites

pip install build twine

A PyPI account with two-factor authentication enabled (mandatory), and an API token from Account settings → API tokens. When uploading, the username is literally __token__ and the password is the token.

Release checklist

  1. Bump version in pyproject.toml and __version__ in pystepflow/__init__.py. Keep them in step.
  2. Delete stale artifacts — twine upload dist/* uploads everything it finds, including old builds: 
    rm -rf dist build
  3. Build both artifacts: 
    python -m build
  4. Validate the metadata: 
    python -m twine check dist/*
  5. Confirm the static files are bundled. They are not Python and are the easiest thing to lose: 
    python -c "import zipfile; print('\n'.join(zipfile.ZipFile('dist/pystepflow-1.1.0-py3-none-any.whl').namelist()))"
  6. Rehearse on TestPyPI, then install from it into a clean virtual environment and actually run the command: 
    python -m twine upload --repository testpypi dist/*
pip install -i https://test.pypi.org/simple/ pystepflow
  7. Publish: 
    python -m twine upload dist/*
  8. Tag the release: 
    git tag -a v1.1.0 -m "v1.1.0"
git push origin v1.1.0

PyPI releases are permanent. A version can be yanked but never replaced or reused, and a project name is never released once taken. A typo in the description or a broken project URL means shipping a new version to fix it. That is why step 6 is worth the extra few minutes.

17. Troubleshooting

SymptomCause and fix
pystepflow not found The Scripts directory is not on PATH. Use python -m pystepflow.server, or add it.
“Execution exceeded 15s” A slow call, not necessarily a bug. Raise it with --timeout 120.
“Stopped after 5000 steps” An infinite loop, or a genuinely long program. Raise MAX_STEPS in tracer.py if it is the latter.
A variable shows <redacted> Redaction matched its name or value shape. Run with --show-secrets.
No flow graph for a function It exceeds MAX_STATEMENTS (400). The trace still works; only the chart is skipped.
Stepping does not enter a function It is library or C-level code. Only functions defined in the traced source are stepped into, by design.
Output appears all at once Expected at the last step. Step backwards to see output accumulate.
SyntaxError: invalid non-printable character U+FEFF Should not occur — BOMs are stripped on read. If it does, the file reached the tracer by another route; re-save it as UTF-8 without BOM.
